==============================================================================
PROJECT IN BRIEF (what Perimeter is)
==============================================================================

Perimeter is a self-hosted incident-triage tool for Kubernetes microservices. When an alert fires it (1) follows the real call graph from OpenTelemetry trace edges outward from the failing service to find the blast radius (plain breadth-first search, so unrelated noisy services are excluded), (2) ranks and trims the logs, metrics and traces of that blast radius to fit a model's token budget, (3) makes one Groq model call at temperature 0 that must answer in a strict JSON schema, (4) checks every claim in that answer against the evidence it cites (the fact-checking validator), (5) lets a human review, edit and finalize the draft in a role-gated dashboard, and (6) pages the best-fit 1-2 responders on Telegram based on skill, seniority and availability. It runs inside the organisation's own cluster, so raw telemetry never leaves it; only a small summary goes to the model provider. It is evaluated by injecting known faults with Chaos Mesh and scoring the output against the injected ground truth. The proposal's target: under 90 seconds from alert to a reviewed draft (not measured yet). Accuracy claims are for a controlled test environment, never production.

Access model: 5-digit ID = Admin (sees everything, manages the Team Directory and leave); 6-digit ID = Team member (sees only incidents on services their team owns). The ID length is only a hint; the server checks the role in the database on every request.

Stack: Python (FastAPI) correlation engine; Node.js/Express/TypeScript BFF with PostgreSQL; React + Vite + TypeScript dashboard; Docker Compose locally; Minikube then EKS; GitHub Actions CI.

- GET /api/v1/incidents -> {incidents: [{id, title, status, alert_service_id, blast_radius, root_cause_draft, created_at, service_name, owning_team_id}]}. root_cause_draft is JSON TEXT: {"status": "ok"|"flagged", "draft": {...per docs/llm-output-schema.md}, "validation": {"claims": [{"id","supported","reasons","rendered_text"}], "issues": [{"rule","message"}], "timeline_warnings": [row indexes]}} or null when no draft exists.

NEW API 1 - edit and finalize (built by JYOTHI Task 1, used by SRIRAM Task 2)
  PATCH /api/v1/incidents/:id/draft
  Body (at least one key): {"hypothesis": {"summary"?: string<=500, "root_cause_service"?: string, "cascade_path"?: string[] (>=1), "confidence"?: "low"|"medium"|"high"}, "postmortem": {"summary"?: <=800, "impact"?: <=500, "contributing_factors"?: string[] (each <=300), "next_steps"?: string[] (each <=300)}, "finalize"?: boolean}
  Unknown keys or wrong types -> 400. Unknown incident, or an incident the caller may not see -> 404 for unknown / 403 for another team's. Admin may always edit; a team member only for incidents on services their team owns; once final, only an admin may edit (a team member gets 409).
  Success 200: {"incident": {id, title, status, alert_service_id, blast_radius, root_cause_draft, reviewed_draft, reviewed_by, reviewed_at, finalized_at, created_at, service_name, owning_team_id}}. The original model draft in root_cause_draft is never modified; edits go in reviewed_draft (JSON object with the edited hypothesis/postmortem fields merged over the draft). finalize=true sets status 'final' and finalized_at. GET /incidents returns the same new fields.

NEW API 2 - services (built by JYOTHI Task 2, used by her Team dashboard)
  GET /api/v1/services -> {services: [{id, name, owning_team_id, tier}]}. Admin: all services. Team member: only services their team owns.

NEW API 3 - evaluation results (built by GOUTHAM Task 2, used by his results screen)
  GET /api/v1/evaluation/results (admin only; team members get 403) -> {"runs": [{"source": file name, "run_at": ISO string, "environment": string, "dry_run": boolean|null, "notice": string, "total": number, "passed": number, "pass_rate": number, "results": [raw per-scenario objects from the file]}]}. Reads benchmark_results.json and chaos_run_*summary.json from the directory in the env var EVALUATION_RESULTS_DIR (default: evaluation/benchmark/results in the repo). A file that is missing or unparsable is skipped, not a 500.

- Branch from develop, squash-merge into develop; develop is merged into main by the lead for releases (see CONTRIBUTING.md).

- Move to the next milestone when the current one passes its "Done when" checks, not on a date.
